# AEGENTIX Cybercore Intelligence Pipeline Specification v2

**Status:** Implementation contract

**Version:** 2.0.0

**Date:** 2026-08-06

## Purpose

This specification extends `CYBERCORE/opportunity_intake` with three deterministic layers: authoritative source verification, strategic intelligence scoring, and commercialization routing. The implementation remains event-first and preserves the mandatory human authorization boundary.

> Discovery does not imply validation. Validation does not imply strategic fit. Strategic fit does not imply authorization. Authorization records a scoped human decision and does not itself execute an external action.

## Layer contracts

| Layer | Required inputs | Durable outputs | Automatic state ceiling |
|---|---|---|---|
| Source verification | Existing record, evidence batch, authoritative HTTPS source, retrieval timestamp, per-field checks | `source_evidence[]`, strict `validation`, temporal status, verified official metadata | `VALIDATED` |
| Strategic intelligence | Strictly verified record and versioned policy | Five 0–100 dimensions, weighted score, policy version, explanation, priority recommendation | `STRATEGIC_MATCHED` |
| Commercialization routing | Verified record, completed intelligence score, deterministic route policy | Candidate paths, primary path, route rationale, readiness, Treasury Labs handoff gate | `HUMAN_REVIEW_REQUIRED` only when open and actionable |

## Source verification

### Evidence batch

Each evidence item identifies an existing record by `record_id` or unique intake title and contains:

- `source_authority`, one or more authoritative HTTPS `source_urls`, and `retrieved_at`;
- an immutable evidence classification;
- verified official title, issuer, identifier, dates, status, value, eligibility, and submission method when present;
- explicit booleans for `issuer_verified`, `identifier_verified`, and `deadline_verified`;
- a concise evidence summary and confidence value;
- a canonical evidence hash generated by the system.

### Verification decision

Strict record validation reaches `VERIFIED` only when all of the following are true:

1. an authoritative HTTPS source is present;
2. `retrieved_at` is a valid UTC timestamp;
3. issuer, identifier, and deadline are present;
4. the evidence marks issuer, identifier, and deadline as directly verified;
5. the evidence classification is a specific opportunity or forecast rather than a broad program category;
6. the evidence is structurally valid and internally consistent.

Program portfolios, broad categories, and records without an exact authoritative match retain evidence but remain `NEEDS_SOURCE_VERIFICATION`. They cannot enter an actionable commercial route.

### Temporal status

| Temporal status | Rule | Commercial consequence |
|---|---|---|
| `OPEN` | Deadline is after the evaluation date | May enter human review after scoring and routing |
| `DEADLINE_TODAY` | Deadline date equals the evaluation date | May enter expedited human review; no assumption is made about cutoff time |
| `CLOSED` | Deadline is before the evaluation date | Archived/monitor-only; no new submission route |
| `FORECAST` | Verified forecast that is not yet soliciting applications | Monitor-only |
| `PROGRAM_ONLY` | Verified issuer/program category without one specific solicitation | Source-discovery only |
| `UNKNOWN` | Evidence cannot establish temporal actionability | Source-verification queue |

## Strategic intelligence

The score is deterministic and policy-based, not a statistically calibrated prediction. Every score stores its policy version and dimension explanations.

### Dimensions

| Dimension | Range | Meaning |
|---|---:|---|
| `sector_fit` | 0–100 | Match between opportunity sector and the versioned AEGENTIX alignment taxonomy |
| `revenue_probability` | 0–100 | Policy estimate of near-term commercial conversion based on route type and temporal status |
| `funding_probability` | 0–100 | Policy estimate of funding/award accessibility based on instrument, status, and evidence completeness |
| `implementation_complexity` | 0–100 | Delivery burden; higher is harder |
| `strategic_alignment` | 0–100 | Alignment derived from explicit strategic tier and priority signals |

### Weighted score

```text
Opportunity Intelligence Score =
  sector_fit × 0.25
+ revenue_probability × 0.20
+ funding_probability × 0.20
+ (100 - implementation_complexity) × 0.15
+ strategic_alignment × 0.20
```

The score is rounded to one decimal place. Priority recommendations are `P0` for scores of at least 80, `P1` for scores of at least 65, and `P2` otherwise. A score is not computed unless the strict verification decision is `VERIFIED`.

### Policy configuration

A versioned JSON policy owns weights, thresholds, temporal adjustments, route adjustments, and sector keyword matches. Unknown sectors receive the documented policy default rather than an invented per-record value.

## Commercialization routing

### Eligible paths

| Opportunity signal | Candidate path |
|---|---|
| Grant or cooperative agreement | `grant`, with `research_partnership` when partnership/consortium delivery is indicated |
| Standard procurement | `prime_bid`; add `subcontractor_position` when market entry indicates it |
| CSO, challenge, or prize | `prototype_demonstration` |
| Supplier channel | `supplier_contract` |
| Consulting procurement | `consulting_engagement` |
| Technology need or commercialization program | `licensing_commercialization` |

### Readiness states

| Route status | Condition | Treasury Labs handoff |
|---|---|---|
| `READY_FOR_HUMAN_REVIEW` | Strictly verified, scored, specific path, and temporal status `OPEN` or `DEADLINE_TODAY` | `HUMAN_APPROVAL_REQUIRED` |
| `MONITOR_FORECAST` | Verified forecast | `BLOCKED` |
| `CLOSED_NO_ACTION` | Deadline passed or source says closed/inactive | `BLOCKED` |
| `PROGRAM_DISCOVERY_ONLY` | Program/category evidence without a specific opportunity | `BLOCKED` |
| `SOURCE_VERIFICATION_REQUIRED` | Strict verification incomplete | `BLOCKED` |
| `NO_ROUTE_IDENTIFIED` | Verified and scored but no defensible path | `BLOCKED` |

Treasury Labs receives no automatic API call, message, financial commitment, bid, registration, or submission. A ready record moves only to `HUMAN_REVIEW_REQUIRED`. Any downstream action must pass the existing authorization artifact integrity, scope, freshness, and expiry checks.

## Events

The pipeline emits and persists these additional Cybercore events:

- `OPPORTUNITY_SOURCE_VERIFIED`
- `OPPORTUNITY_INTELLIGENCE_SCORED`
- `OPPORTUNITY_COMMERCIAL_ROUTE_IDENTIFIED`

Each event carries the complete updated record snapshot so Kernel replay reconstructs the same state without dispatching side effects.

## Operator interface

```bash
aegentix_cybercore_ingest verify --evidence evidence/source-verification-2026-08-06.json
aegentix_cybercore_ingest score --record all
aegentix_cybercore_ingest route --record all
aegentix_cybercore_ingest pipeline --evidence evidence/source-verification-2026-08-06.json
```

Every operation writes a run manifest, appends events, synchronizes durable stage projections, and optionally publishes events to a running Kernel. Kernel publication is fail-open by default and fail-closed when `--kernel-required` is set.

## Authorization binding

The review material hash includes all evidence, verification, intelligence, commercialization, priority, route, and Treasury handoff fields. Any material change after authorization revokes the prior authorization and returns the record to `HUMAN_REVIEW_REQUIRED` before any external action can be considered.
